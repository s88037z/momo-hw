# 題目 A：momo 搜尋頁實作規劃

日期：2026-11-06｜階段：Design / Planning｜實作上限：120 分鐘

## 1. 目標與決策

完成一個以 momo 搜尋結果頁為參考的前端頁面，呈現「主要版面還原＋核心查詢流程」。以一個可驗證的頁面交付，不納入首頁與商品詳情頁。

選擇搜尋頁，是因為重複商品卡適合元件化，搜尋、篩選與排序能呈現狀態一致性（State Consistency）及 AI 產出驗證能力。首頁需要大量活動素材；商品頁是可行替代方案，但本次優先展示查詢流程。

真站搜尋頁包含多列篩選條件（Facets）與服務選項，全部實作會超出時限。因此保留主要視覺結構，只呈現資料真正支援的控制項；縮減的篩選列列入與原站的已知差異，不以無作用的按鈕填補畫面。

## 2. 範圍與視覺基準

| 項目 | 必做範圍 |
| --- | --- |
| 路由 | `/search?q=iphone+17+pro`；根路徑提供進入搜尋頁的最小入口，不製作首頁 |
| 頁面 | 搜尋列、分類導覽、麵包屑、品牌篩選區、排序／價格列、商品網格與分頁 |
| 查詢 | 關鍵字搜尋、品牌單選／取消、價格區間、綜合推薦與價格升降序、分頁、清除篩選 |
| 商品卡 | 本地圖片、促銷標籤、名稱、價格、評分與銷量等代表性資訊 |
| 狀態 | 載入中、無結果、資料錯誤與重試；URL 還原與瀏覽器上一頁／下一頁 |
| 螢幕 | 桌面版還原優先；窄螢幕提供基本重排，不承諾還原 momo 手機站 |

不做：其他進階 Facets、服務條件篩選、月銷量／上市日／評價排序、列表檢視切換、瀏覽紀錄、會員、購物車、結帳、真站 API 與後端服務。

視覺依據為 `.ai/resources/snapshot/search-snapshot.png`，輔以規劃階段已取得的真站畫面。比較時固定 CSS viewport 為 1440 × 1000；原圖的影像像素不直接視為 CSS 尺寸。優先比對內容寬度、篩選區密度、灰底排序列、粉紅選取態、桌面六欄商品網格，以及圖片／文字／價格比例。

商品區要包含完整商品卡，不能只完成截圖中露出的圖片上緣。素材使用本地檔案並記錄來源，執行時不依賴 momo 圖片服務；參考圖若需交付，須另行納入可提交的位置。

## 3. 技術與狀態分工

採用 **Next.js App Router、TypeScript、Tailwind CSS、TanStack Query、MSW**。以靜態輸出（Static Export）交付，查詢於瀏覽器執行，不使用 API Routes、Server Actions 或動態伺服器資料讀取。

| 責任 | 放置位置 |
| --- | --- |
| 已套用的 `q / brand / min / max / sort / page` | URL，作為查詢條件的單一來源 |
| 結果、總數、載入／錯誤狀態 | TanStack Query；Query Key 使用正規化後的完整查詢條件 |
| 未送出的搜尋／價格輸入、選單展開 | 元件狀態（Local State） |
| 商品與查詢運算 | 獨立的 Mock 資料與純函式 |

**Zustand 暫不加入**：本次沒有需要獨立維護的跨頁共享狀態。避免把同一份查詢條件同時存進 URL、Query 與 Store。

TanStack Query 集中管理非同步資料狀態，透過 `fetch` 呼叫同源 `/api/products`，由 MSW 在瀏覽器攔截並回傳固定資料。此路徑是 Mock HTTP 合約，不是 Next.js API Route，也不需要後端。開發與靜態展示版均啟用 Mock，等待 `worker.start()` 完成後才掛載查詢元件，避免首個請求搶先送出。不加入 SSR prefetch／hydration。

原方案為直接呼叫本地 Promise service，整合成本較低；使用者在第一批開始前選擇 MSW，理由是熟悉該工具，且希望保留一般 HTTP 呼叫與未來 API 替換邊界。代價是 Worker 檔案、啟動等待與展示環境的整合驗證。資料篩選邏輯保持獨立，供 handler 與測試重用。這是純 Mock 展示應用，刻意不套用「production 停用 MSW」的一般設定。

建議分工（位於 `src`）：`app/search` 組合頁面與 URL；`features/search` 放控制項、參數解析與查詢邏輯；`features/products` 放商品模型、HTTP 呼叫與卡片；`mocks` 放固定資料、handlers 與 Worker 啟動；`public` 放素材與 Worker 腳本。不先建立通用 Facet／Plugin 引擎。

Next.js 注意事項：讀取 `useSearchParams` 的 Client Component 使用適當的 Suspense 邊界；本地圖片使用相容靜態輸出的設定；盡早執行 production build，避免只在 dev 模式可用。

## 4. 行為約定與資料

- 準備約 24 筆固定 Mock 商品，每頁 12 筆。預設搜尋可包含手機與不同品牌配件，確保品牌篩選與分頁可示範；名稱與 keywords 做基本比對，不做模糊搜尋。
- 搜尋與價格輸入以送出／確認套用。價格須為非負有效數字，且最低價不高於最高價；無效輸入顯示提示，不更新 URL。
- 搜尋、品牌、價格或排序改變時，重設為第 1 頁；排序保留其他條件。「綜合推薦」使用固定資料順序，價格相同時以固定 ID 排序。
- 未知排序值、無效頁碼有預設處理；結果數與分頁由資料計算，空結果不顯示可前進的分頁，不複製真站的虛構總數。
- 清除篩選保留目前關鍵字，重設品牌、價格、排序與頁碼。上一頁／下一頁後，控制項與結果必須同步。
- 錯誤與延遲透過測試替身或開發設定重現，不使用隨機失敗；正式展示不加入與購物無關的除錯控制項。

## 5. 120 分鐘實作順序

| 時間 | 可檢查的產出 |
| --- | --- |
| 0–15 分 | 建立專案、靜態輸出設定、搜尋路由與 Mock 模型；完成初次 build |
| 15–45 分 | 完成頁面結構、商品卡與本地素材，取得第一張可比較畫面 |
| 45–75 分 | 串接 URL、Mock Query、品牌／價格／排序與分頁，完成核心流程 |
| 75–95 分 | 驗證參數與邊界狀態，加入核心流程測試並修正問題 |
| 95–110 分 | 固定尺寸截圖比對，修正影響最大的版面差異 |
| 110–120 分 | 完成 README、差異與 AI 協作紀錄，執行最終 build／檢查並提交 |

停損：第 75 分鐘後不增加功能。落後時先縮減促銷樣式、裝飾導覽與窄螢幕細節；若核心查詢仍未完成，再降級分頁並明確記錄未交付項目。保留核心流程、production build 與交付說明的時間。

本文件屬規劃階段。本輪不建立 commit；正式實作記錄實際開工與 first commit 時間，遵循題目的計時方式，不將預先完成的程式包裝成計時內產出。上表時段包含人工 review、必要修正與文件紀錄，等待回覆不視為暫停計時；必要時縮減範圍。120 分鐘到點停止修改並如實記錄未完成項目，尚未通過 review 的變更不得為了趕時間直接 commit。

## 6. 驗收與 AI 協作

核心驗收：搜尋 → 品牌／價格篩選 → 排序 → 分頁 → 重新整理 → 瀏覽器返回，結果、控制項與 URL 一致；另驗證空結果、非法價格與無效 URL 參數。具備基本鍵盤操作、表單標籤與選取狀態。

驗證以一條核心端到端測試（E2E）及必要的查詢邏輯測試為主；完成 build、型別／lint 檢查，檢查 console 與 Network 無錯誤或真站 API 呼叫。視覺比對須列出保留的差異，不宣稱完整 pixel-perfect 還原。

提交內容包含 source、Git history、啟動方式、範圍與差異、驗證結果及精簡協作紀錄。未來接入 API 時替換 Mock service；新增多類別商品時才擴充 Facet schema；出現跨頁購物車需求時再評估 Zustand。

## 7. 每批實作、人工 Review 與 Commit 流程

目的：讓候選人逐批判斷 AI 的實作結果與技術取捨（Engineering Judgment / Tradeoff），留下決策依據與驗證證據。

1. **開始前說明本批範圍**：列出要完成的行為、預計影響的檔案／模組、驗收方式與預估時間。一批解決一個可獨立 review 的問題，不混入無關重構或下一批功能；以單一 Agent 配合人工 review 為起點。
2. **先釐清未決的技術選擇**：若會改變架構、依賴、狀態責任、使用者行為或交付範圍，先提出選項、建議與代價，等待使用者決定後再執行相關變更。已定案的選擇及範圍內的一般實作細節可直接執行，不為命名或排版反覆中斷。
3. **實作並完成驗證**：只執行本批已確認的範圍；遇到必須擴大範圍的問題，先提出影響與建議。review 前提供可執行、可檢查的結果及必要的測試／畫面證據。
4. **留下文件與簡述結果**：每批建立 `docs/implement-steps/NN-short-name.md`，記錄 scope、技術選擇與理由、驗證結果、已知限制、待 review 重點；在回覆中簡述相同資訊並連結文件。
5. **等待人工 Review**：使用者判斷是否符合範圍、行為與技術方向。需要修正時沿用同一份紀錄補充回饋與驗證，不把 AI 自行檢查視為人工核可，也不逕自展開下一批。
6. **核可後才 Commit**：使用者明確同意本批提交後，才提交該批程式與紀錄；只納入已 review 的變更，不順帶提交其他 staged 檔案。提交前更新紀錄中的核可結果，提交後在回覆提供 commit hash，再依使用者指示進入下一批。

建議四個 review 節點：① 專案與 Mock 資料基礎；② 搜尋頁視覺與商品卡；③ URL 與核心查詢流程；④ 邊界驗證、視覺修正及交付文件。節點對應第 5 節的時段，不要求每個小調整都單獨 review／commit。

每份紀錄保持精簡，優先保留採納／拒絕方案、人工回饋與修正證據，不貼完整對話。如實標記 Agent co-authored 資訊。格式與狀態規則見 [實作步驟紀錄](./implement-steps/README.md)。

技術依據：[Next.js Static Export](https://nextjs.org/docs/app/guides/static-exports)、[TanStack Query Functions](https://tanstack.com/query/latest/docs/framework/react/guides/query-functions)、[MSW Browser Integration](https://mswjs.io/guides/integrations/browser)。
